## 實驗 1：CJK 段落切塊

**假設**：`rag.py` `_SECTION_HEADINGS` 只有英文正則,中文說明書會 fall back 成單一 `BODY` chunk,喪失節結構,傷害檢索品質(尤其 TW 重心)。

**改動**：`backend/ai_engine/rag.py` `_SECTION_HEADINGS` 每個 canonical label 的正則加上中/日文段落標題的 alternation,並新增 `DRAWINGS` label：

| label | 新增匹配（節錄） |
|---|---|
| FIELD_OF_INVENTION | 技術領域 / 技术领域 / 技術分野 |
| BACKGROUND | 先前技術 / 背景技術 / 背景技术 / 發明背景 |
| SUMMARY | 發明內容 / 发明内容 / 発明の概要 |
| DRAWINGS（新） | 圖式簡單說明 / 附圖說明 / 附图说明 / 図面の簡単な説明 |
| DETAILED_DESCRIPTION | 實施方式 / 具體實施方式 / 具体实施方式 / 発明を実施するための形態 |
| CLAIMS | 申請專利範圍 / 权利要求書 / 权利要求 / 特許請求の範囲 |

依 專利法施行細則 §17 的明細書結構。刻意排除過於泛用的 `實施例`/裸 `請求項`（會在內文誤觸發切點）。

**測試**：`tests/unit/test_rag_chunking_robustness.py` 新增 4 個測試（TW 切六節、before/after 對照、CN/JP 也能切、BODY 不再出現）。

**量到的數據**（同一份 TW 範例說明書）：

```
BEFORE（英文-only）：section count = 1   → 單一 BODY chunk
AFTER （加 CJK）   ：section count = 6   → FIELD_OF_INVENTION, BACKGROUND,
                                          SUMMARY, DRAWINGS,
                                          DETAILED_DESCRIPTION, CLAIMS
```

**相容性**：英文正則原樣保留(英文說明書行為不變);純加 alternation。`tests/unit` 全綠。

## 實驗 2：retrieve() 前案日期硬過濾

**假設**：前案必須早於申請/優先權日（專利法 §22/§23）才能據以核駁。`rag.retrieve()` 只用 jurisdiction 過濾,chunk metadata 雖有 `pub_date` 卻沒拿來擋晚於申請日的前案——這是法律正確性缺口。

**改動**：`backend/ai_engine/rag.py`
- `retrieve()` 新增 optional `max_pub_date: date | datetime | str | None = None`（案件申請/優先權日）。
- 新增 helper `_coerce_date` / `_chunk_pub_date` / `_passes_prior_art`。
- filter 啟用時 over-fetch（`fetch_k = max(top_k*4, 20)`,因 memory store 的 metadata filter 只支援精確比對,無 range query）,後過濾再截斷至 `top_k`。
- **fail-closed**：`pub_date` 缺失/無法解析的 chunk 在 filter 啟用時一律剔除(無法證明早於申請日的前案,寧可不呈現)。
- **strict**：`pub_date == 申請日` 也不算前案(須嚴格早於)。

**測試**：`tests/unit/test_rag_chunking_robustness.py` 新增 4 個測試(排除晚於申請日的前案、接受 date/datetime/str 三型輸入、fail-closed + strict 邊界、預設 None 行為不變)。

**量到的數據**：索引 TW-OLD(2019)、TW-NEW(2026) 兩件;`max_pub_date="2023-06-01"` → 只剩 TW-OLD,TW-NEW 被剔除。三種輸入型別結果一致。

**相容性**：預設 `None` = 完全等同舊行為(向後相容)。`tests/unit` 全綠。
**注意**：此能力目前**未接進 live OA 分析流程**——需要案件的申請/優先權日作為輸入。wiring 到 orchestrator/oa_analyzer 列為下一步(分冊00 §三-A-1)。

## 實驗 3：verify_citations 跨管轄引用洩漏偵測

**假設**：`verify_citations` 的硬牆把 `35 U.S.C. § 103` 當「可驗證法條」白名單保留。但在 **TW 申復書**中引美國法是法律錯誤(美國法在 TIPO 無效力),應比照未接地引用剝除。

**改動**：`backend/ai_engine/oa_analyzer.py`
- 新增 `_US_STATUTE_RE` 與 `_is_foreign_statute(citation, jurisdiction)`。
- `verify_citations()` 新增 optional `jurisdiction: str | None = None`。當 `jurisdiction=="TW"` 且 citation 命中美國法樣式 → 進 `invalid`(被剝除)並另記入新欄位 `cross_jurisdiction_citations`(讓專利師看到「為何消失」而非默默不見)。
- result dict 新增 `cross_jurisdiction_citations` 欄位(additive;HTTP 端點回傳 plain dict,消費端讀所需 key,不破壞)。

**測試**：`tests/unit/test_invariant_citation_grounding.py` 新增 3 個測試(TW 案剝除美國法但保留 專利法第22條第2項 與 grounded slot、未指定 jurisdiction 時維持舊行為、US 案保留美國法)。

**量到的數據**：TW 草稿同時含 `[GROUNDED_REF_1]`、`專利法第22條第2項`、`35 U.S.C. § 103`：
- `jurisdiction="TW"` → 美國法進 `cross_jurisdiction_citations` + `invalid`,cleaned text 不再含 `U.S.C`;TW 法條與 grounded slot 保留;`valid=False`。
- 不傳 jurisdiction（預設）→ 美國法仍在 `valid_citations`,`valid=True`（舊行為）。
- `jurisdiction="US"` → 美國法保留。

**相容性**：預設 `None` = 等同舊行為,既有 33 個 verifier/citation/anthropic 測試全綠。

## 實驗 4：把 jurisdiction 接進 live 流程（讓實驗3 真正生效）

**假設**：實驗3 的能力若沒接進 HTTP/orchestrator 就只是 dormant。orchestrator 已用 `_jurisdiction_for_patent(req.target_patent_no)` 推導管轄(deadline 步驟在用),可同源接進 verify。

**改動**（全部 additive、向後相容）：
- `backend/ai_engine/main.py` `VerifyRequest` 加 `jurisdiction: str | None = None`;endpoint 將 `req.jurisdiction` 傳入 `verify_citations`。
- `backend/gateway/orchestrator.py` verify 步驟前算 `case_jurisdiction = _jurisdiction_for_patent(req.target_patent_no)`,加入 verify payload。

**測試**：新增 `tests/integration/test_verify_jurisdiction_endpoint.py`(2 個)——POST `/v1/verify_citations` 帶 `jurisdiction="TW"` → 美國法被剝除且回報於 `cross_jurisdiction_citations`,TW 法條/grounded slot 保留;省略 jurisdiction → 維持舊行為。鎖住整條 HTTP 契約。

**相容性**：`VerifyRequest` 非 `extra=forbid`,加欄位安全;orchestrator saga 測試(會 mock `/v1/verify_citations`)通過,證明新 payload key 不破壞。預設不傳時行為不變。

**結果**：實驗3 現在對所有經 orchestrator 的 TW 案**自動生效**——專利師不需手動指定,管轄由 target patent 推導。

**注意**：`_jurisdiction_for_patent` 目前是 patent_no 前綴啟發式(orchestrator.py 既有 stub,docstring 註明 production 應讀 case-management 記錄)。管轄推導的正確性繼承此 stub 的限制。

## 實驗 5：§26 請求項支持度 lint（撰稿側缺口）

**假設**：知識地圖把「§26 支持度 lint」列為撰稿側 🔴 缺口。專利法 §26 II 要求請求項
「為說明書所支持」;最常見且確定性可檢查的 smell 是**請求項出現了說明書從未描述的技術
特徵**。這正適合「確定性 lint 先於 LLM」。

**改動**：新增純解析模組 `backend/ai_engine/claim_support.py`（與 `claim_tree.py`/
`element_table.py` 同血統:自含、無 LLM、有 CLI）：
- `check_claim_support(claims, spec_text)` → 每個請求項一個 `ClaimSupport`（support_ratio、
  unsupported_fragments、is_independent、flagged）。
- 支持單元:拉丁字以**詞**為單位、CJK 以**字元 bigram** 為單位(unigram 太寬鬆);bigram
  比對涵蓋率還原成可讀的「未支持片段」。
- 先剝除請求項交叉引用樣板（如「如請求項1所述之」/「according to claim 1」/「一種」preamble）
  與結構性樣板字（所述/其中/wherein/comprising…),避免誤報。
- **誠實範圍**:這是 LINT 不是法律判斷——只看「說明書字面有沒有」,同義詞/上下位的實質
  支持看不出來,故會有 false positive,一律標「待專利師覆核」。

**測試**：`tests/unit/test_claim_support.py`（8 個）——全支持不誤報、引入說明書未提及的
新詞（區塊鏈結算）被標出且交叉引用樣板不誤報、英文路徑（piezoelectric/pump 被標）、空
說明書、roll-up、空 claims 安全、決定性。

**量到的數據**（DEMO,TW）：claim 1（特徵全在說明書）support=0.974、未標記;claim 2
（引入「區塊鏈結算」）support=0.35、標記片段 `['透過區塊鏈結算進行計費']`。

**相容性**：全新模組,未接 orchestrator(callers 顯式 import),不觸及任何不變量。
**下一步**:接成 `/v1/claim_support` 端點 + 前端撰稿視圖的 §26 徽章;之後可疊一層 LLM 對
被標片段做「語意是否仍受支持」的第二意見(但 lint 永遠是第一道、確定性那道)。

## 實驗 6：強化 `_jurisdiction_for_patent`（讓實驗3/4 更可靠）

**假設**：實驗3/4 的跨管轄引用偵測與 deadline 都依賴 orchestrator 的
`_jurisdiction_for_patent`,而它原本取 `patent_no[:2]`(不分字母/數字),且**無任何直接測試**。

**改動**：`backend/gateway/orchestrator.py`
- 改取**前導字母碼**(`TWI123456`→TW、`US-9,999,999`→US),純數字號(`1234567`)不再
  以前兩位數字巧合命中,乾淨 fallback 到 TW。
- PCT(`WO…`)無單一國家答辯期,路由到事務所本國(TW)。
- 抽出 `_KNOWN_JURISDICTIONS` 常數。

**測試**：新增 `tests/unit/test_jurisdiction_for_patent.py`（14 參數化 + 1 回歸）——涵蓋
US/TW(I/M)/EP/JP/CN/KR、大小寫、空白、WO→TW、不支援國(DE)→TW、純數字→TW、digit-led
不巧合命中。

**相容性**：對所有正常輸入結果不變(只是更穩健);全回歸綠。
