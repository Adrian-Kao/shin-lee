This directory is the single source of truth for every fixture the
PatentMind eval harness and integration tests load.

deadline logic across every rejection type the pipeline currently
emits.

## Schema (every case dict)

See the module docstring of `synthetic_cases.py` for the canonical
schema. Headline fields:

```python
{
  "case_id": "CASE-DEMO-031",
  "patent": {
    "patent_no": "TW2026100001",
    "title": "...",
    "abstract": "...",
    "claims": ["請求項 1 ...", ...],
    "spec_text": "【發明所屬之技術領域】...",
    "filing_date_roc": (113, 4, 20),         # (民國年, 月, 日)
    "publication_date_roc": (115, 6, 1),
    "ipc": ["H01M4/04", "H01M10/0562"],
    "applicants": ["晶碩固態能源股份有限公司"],
    "inventors": ["王立翔"],
    "jurisdiction": "TW",                     # "TW" | "US" | "EP" | "JP"
  },
  "oa": {
    "doc_type": "初審審查意見通知函",
    "date_roc": (115, 2, 14),
    "doc_no": "11520214011",
    "examiner": "林雅婷",
    "response_months": 2,
    "rejections": [
      {
        "statute": "專利法第22條第2項",
        "rejection_type": "103_obviousness",
        "affected_claims": [1, 2],
        "cited_prior_art": ["TW202011111", "JP2022100001"],
        "argument": "...",
      },
    ],
  },
  "reexam": None,                              # or dict, same shape as `oa` + outcome
}
```

`rejection_type` MUST be one of the `RejectionType` enum values in
`backend/shared/models.py`:

| enum value          | Used by                                          |
|---------------------|--------------------------------------------------|
| `102_novelty`       | TW §22-1, US §102                                |
| `103_obviousness`   | TW §22-2, US §103                                |
| `112_indefiniteness`| US §112(b) general                                |
| `antecedent_basis`  | TW §26-2 (缺先行詞), US §112(b) antecedent       |
| `101_subject_matter`| TW §24, US §101                                  |
| `double_patenting`  | (reserved)                                       |
| `other`             | TW §26-1, §26-4, §32; anything not above         |

Patent numbers use ranges chosen to not collide with the baseline:
TW → `TW2026100001+`, US → `US18000001+`.

## Adding a new case

1. Open `synthetic_cases.py`, scroll to the end of the `CASES` list.
2. Copy an existing dict that's closest to your new case shape and
   adjust fields. Bump the `case_id` and `patent_no` monotonically.
3. Verify in a python REPL:
   ```python
   from data.cases.synthetic_cases import CASES
   assert len({c["case_id"] for c in CASES}) == len(CASES)
   assert len({c["patent"]["patent_no"] for c in CASES}) == len(CASES)
   ```
4. Re-render and re-index:
   ```bash
   python scripts/render_cases.py    # regenerates per-case folders + manifest.json
   python scripts/eval_cases.py --mode mock --case CASE-DEMO-NNN   # smoke test
   ```
5. Run the unit + integration suites:
   ```bash
   pytest tests --tb=line -q   # expect ≥ 128 passed
   ```

## Regenerating fixtures

### Per-case `patent.txt` / `oa.txt` / `reexam.txt`

```bash
python scripts/render_cases.py
```

Deterministic — re-run after editing `synthetic_cases.py`. Rewrites
`manifest.json` too.

### Binary adversarial fixtures (PDFs)

```bash
python scripts/generate_test_data.py
```

Idempotent — only writes files that don't already exist. Delete a file
first if you want to force regeneration. See the script's docstring for
the password used on `pdf_password_protected.pdf`.

### Text adversarial fixtures

Hand-edited. The `.md` companion file next to each fixture documents
what it tests, what behavior is expected, and which test consumes it.

## Known mock-LLM weaknesses surfaced by the 80-case eval

When running `python scripts/eval_cases.py --mode mock` against all 80
cases, the mock parser correctly classifies 96% of rejection types but
shows specific weaknesses worth flagging for the real-LLM regression
baseline:

1. **Edge case 079 (no rejections)** — the mock falls through to its
   default `103_obviousness` instead of emitting an empty rejection
   list. Real Sonnet 4.6 should correctly emit `[]`.
2. **§26-2 antecedent_basis claim-set accuracy** — the mock greedily
   takes the FIRST `請求項 N` near the keyword, which misses cases
   where the rejection spans multiple claims (e.g. CASE-DEMO-029).
3. **Multi-rejection cases (067–072)** — claim sets per rejection sometimes
   mis-aggregate because the mock can't see which claim cluster
   belongs to which statute paragraph.
4. **US/TW mixed corpora** — Cyrillic homoglyph fixture (test 5) does
   not crash but produces a generic rejection because the keyword
   detector does not see the literal `Claims` / `35 U.S.C.` strings.

These are documented limits of the mock; they are NOT bugs in the
parser surface. The real Anthropic backend (`LLM_MODE=anthropic`) is
expected to handle all four cleanly.
