# 04 — 分散式與可擴展架構 (Distributed & Scalable Architecture)

> 受眾：PatentMind 開發 / 維運工程師。
> 範圍：把現有單機 POC（docker-compose）演進到生產級分散式系統，
> 同時不破壞兩條鐵律——**一請求一稽核列 (one-audit-row-per-request)**
> 與 **per-tenant 物理隔離**。
> 對照文件：`CLAUDE.md`（不變量 §4）、`docs/ARCHITECTURE.md`（Q1/Q5/Q13/Q15）、
> `docs/PHASE3_MIGRATION.md`、`docs/DELIVERY_RUNBOOK.md`。

## 30 秒摘要 (TL;DR)

PatentMind 的兩個運算層（gateway :8010、ai_engine :8011）**設計上已經接近無狀態 (stateless)**——
所有可變狀態都被刻意外推到後端基礎設施（Postgres audit、Redis、Qdrant、MinIO WORM）。
這意味著「水平擴展 (horizontal scaling)」的工程量主要不在改業務碼，而在
**(a) 把 in-memory 後端全部切到共享後端 (`*_BACKEND=redis/postgres/qdrant/s3`)**，
以及 **(b) 把有狀態服務升級成高可用 (HA) 叢集**。

真正的架構難點不是「能不能加副本」，而是專利事務所場景的三條物理約束：
**機密案不可離機/離境**、**租戶間絕對隔離**、**稽核鏈不可竄改且可全域驗證**。
這三條把「拓樸 (topology)」從一個純粹的擴展問題，變成一個
**資料落地邊界 (data-residency boundary) + 信任域 (trust domain) 切割問題**。

### 3 個關鍵 takeaway

1. **Stateless 運算層 + 共享狀態後端 = 水平擴展幾乎免費，但有兩個陷阱。**
   陷阱一：rate-limit / quota / cost-breaker 的 in-memory 計數器在多副本下會各算各的、
   超賣配額——必須走 `RATE_LIMIT_BACKEND=redis`（已實作 Lua 原子 reserve）。
   陷阱二：審計 hash chain 是**全域單鏈 (global single chain)**，多寫入者並發會搶同一個
   `prev_row_hash` 而分叉——現況靠單一 writer 的 `RLock` 序列化，跨副本需要把
   chain 的「取 prev → 算 hash → insert」改成 DB 端原子序（見 §5）。

2. **機密性驅動拓樸，不是擴展驅動拓樸。** 正確的生產形態是
   **「雲端控制平面 + 多個地端資料平面 (on-prem data plane)」**：
   每個事務所（或每個高機密分所）一套地端 ai_engine + Qdrant + Ollama，
   機密案的推論流量**永不離開該所機房**（不變量 #7 `LOCAL_LLM_FOR_SECURITY_LEVELS`）；
   只有非機密案、且經 redaction 後的 retrieval 結果才允許出機房打雲端大模型（Q3）。

3. **稽核與 WORM 的分散式一致性是最硬的限制，要先設計再擴展。**
   現有 audit chain per-tenant、WORM Merkle 段鏈、write-ahead outbox 已經把
   「exactly-once 稽核」做對了——但它們都假設**單一寫入點**。
   分散式化的正解不是「讓多節點同時寫一條全域鏈」，而是
   **per-tenant 分鏈 + 各自封存 + 中央只做全域驗證 (verify, 不 write)**（見 §4）。

## 1. 現況盤點：有狀態 vs 無狀態

### 1.1 元件狀態盤點表

| 元件 | 層 | 狀態性 | 狀態存哪 | 可水平擴展？ | 瓶頸 / 風險 |
|------|----|--------|----------|--------------|-------------|
| **gateway** `:8010` | 運算 | **準無狀態** | 業務狀態全外推；唯一 in-process 狀態是 rate-limit/quota/cache 計數器（可切 redis） | ✅ 可多副本 | in-memory 計數器切 redis 前不能擴；audit writer 持單一 DB 連線 + `RLock` |
| **ai_engine** `:8011` | 運算 | **無狀態**（不變量 #2） | 不寫任何業務 DB；只寫 RAG 向量 | ✅ 可多副本 | 純無狀態；瓶頸在下游 LLM / Qdrant，而非自身 |
| **Postgres** (audit) | 狀態 | **強狀態** | append-only 表 + hash chain（`AUDIT_BACKEND=postgres`） | ⚠️ 寫入單主 (single primary) | 全系統審計單點；單主寫入；DR RPO 缺口 |
| **Qdrant** | 狀態 | **強狀態** | per-tenant collection 向量（`VECTOR_BACKEND=qdrant`） | ✅ 叢集 + sharding | 千萬級向量單節點查詢慢；per-tenant collection 數量爆炸 |
| **Redis** | 狀態 | **軟狀態** | cache / rate-limit / quota / revocation（`*_BACKEND=redis`） | ✅ Sentinel / Cluster | 單點則所有共享計數失效；故障時 fail-closed 會擋請求 |
| **MinIO** (WORM) | 狀態 | **強狀態（不可變）** | 封存稽核段 + Object Lock（`ARCHIVE_BACKEND=s3`） | ✅ 分散 erasure coding | 合規保存 7 年；Object Lock 一旦 COMPLIANCE 不可逆 |
| **Ollama / Dify** | LLM | 模型權重（唯讀） | 本機模型檔 | ✅ 多副本（GPU 綁定） | GPU 資源；機密案必須地端（不變量 #7） |
| **MaskingStore** (mapping) | 狀態 | **強狀態（機密）** | 可逆遮罩 mapping，SQLite，**強制 on-prem**（`MAPPING_DB_PATH`） | ⚠️ 隨 gateway | 絕不可離機（§9 of CLAUDE.md）；目前綁 gateway 本機檔 |
| **audit outbox** | 狀態 | 軟狀態（暫存） | JSONL flat file（`AUDIT_OUTBOX_PATH`） | ⚠️ per-replica 本機 | 每副本各有一份 outbox，需各自 replay |
| **tenant_dicts** | 設定 | 軟狀態 | per-tenant 遮罩詞庫 JSON（`data/tenant_dicts/`） | ⚠️ 本機檔 | 多副本需共享/同步這些檔 |

> **盤點結論**：運算層（gateway/ai_engine）已被刻意設計成「狀態可外推」，
> 這是 POC 階段最有價值的架構決策。真正阻擋水平擴展的，是**那些目前還綁在
> gateway 本機檔/記憶體的東西**：in-memory 計數器、outbox flat file、
> mapping SQLite、tenant_dicts。其中只有 mapping 因機密約束**不能**集中化，
> 其餘都應外推到共享後端。

### 1.2 兩條不變量對水平擴展的意義

**不變量 #2「AI Engine 無業務狀態」→ ai_engine 是教科書級可擴展層。**
因為它不寫任何業務 DB（唯一例外是 RAG 向量，而那寫進外部 Qdrant），
任何一個 ai_engine 副本處理任何請求結果都一致。可以無腦加副本、放 LB 後面、
甚至按 GPU 可用性彈性伸縮。**這就是把 LLM 推論層做成 stateless 的回報。**

**不變量 #4「一請求一稽核列」→ 對水平擴展是一條約束，不是阻擋。**
它要求的是「每個 gateway 請求，無論成功/失敗/cache hit，恰好產生一列審計」。
多副本下這條依然成立——只要每個副本各自在自己的 try/finally 框內寫一列。
**關鍵風險不在「列數」，而在「鏈的順序」**：所有副本寫進**同一條全域 hash chain**，
而 chain 要求 `row_hash[N].prev == row_hash[N-1]`。多副本並發寫 = 多個寫入者
搶同一個「上一列」，會分叉。

> 對照 `audit.py:write`：現況用 writer 的 `RLock` 把「讀 prev → 算 hash → insert」
> 三步序列化。**單進程內安全；跨進程/跨副本不安全。** 這是 §5 的核心議題。

對照 `rate_limit.py` 的設計註解（Day 13I），作者已經預見這件事：
in-memory 路徑用 `_STATE_LOCK`，redis 路徑用單一 Lua `EVAL` 把原子性
「搬進 redis server」。同樣的思路要套到 audit chain。

## 2. 水平擴展設計

### 2.1 目標拓樸（單一信任域內 / 非機密路徑）

```
                         ┌─────────────────────┐
        SPA :5173 ─────► │  digiRunner :18080   │  (API gateway / OSS)
                         │  （L7 LB + 路由）     │
                         └──────────┬───────────┘
                                    │  round-robin / least-conn
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
       ┌────────────┐        ┌────────────┐        ┌────────────┐
       │ gateway #1 │        │ gateway #2 │        │ gateway #N │   ← stateless replicas
       └─────┬──────┘        └─────┬──────┘        └─────┬──────┘
             └───────────────┬─────┴───────────────┬─────┘
                             ▼                      ▼
                ┌─────────────────────┐   ┌─────────────────────┐
                │  Redis (Sentinel)   │   │ Postgres (Patroni)  │
                │ cache/quota/revoke  │   │  audit + hash chain │
                └─────────────────────┘   └─────────────────────┘
             ┌───────────────┬─────────────────────┬─────┐
             ▼               ▼                     ▼
       ┌────────────┐  ┌────────────┐        ┌────────────┐
       │ ai_engine#1│  │ ai_engine#2│  ...   │ ai_engine#M│   ← stateless replicas
       └─────┬──────┘  └─────┬──────┘        └─────┬──────┘
             └───────────────┴──────┬──────────────┘
                                    ▼
                  ┌──────────────────────────────┐
                  │  Qdrant cluster (Raft, 3+ node)│
                  │  LLM backends (Ollama GPU pool)│
                  └──────────────────────────────┘
```

### 2.2 Session / JWT：本來就無狀態，保持它無狀態

現況 auth 走 JWT（`auth.py`），**不需要 server-side session 黏性 (sticky session)**。
任何 gateway 副本都能驗任何 token。唯一的共享需求是 **JWT 撤銷 (revocation)**：

- `revocation.py` 已支援 `REVOCATION_BACKEND=redis`——撤銷的 jti 進 redis（帶 EX TTL）。
- **多副本必須切 redis**：否則在副本 A logout 的 token，副本 B 還收。
- **改哪裡**：`REVOCATION_BACKEND=redis` + 確保所有副本指向同一 Redis（Sentinel VIP）。

> 不要為了「集中 session」引入黏性 LB——那會讓副本失效時使用者掉線，
> 也違背 stateless 的好處。JWT + redis 撤銷清單就是正解。

### 2.3 Rate-limit / quota / cost-breaker：**必須走 redis 共享**

這是水平擴展的**頭號正確性陷阱**。In-memory 計數器（`rate_limit.py` 的
`_user_rpm` / `_user_daily_tokens` / `_tenant_monthly_tokens` / `_daily_cost_usd`）
是**每副本各一份**。三個具體 bug：

| 控制 | 多副本 in-memory 的錯誤行為 | 正確後端 |
|------|------------------------------|----------|
| Per-user RPM | N 副本 → 實際上限 N×RPM（每副本各自 token bucket） | redis（待補：RPM 也要 redis 化，見下） |
| Per-user 日 token quota | N 副本各自 reserve，集體超賣 N 倍 | `RATE_LIMIT_BACKEND=redis` ✅（Lua `EVAL` 原子 reserve 已實作） |
| Per-tenant 月 cap | 同上，租戶月底破合約上限 | 同上 ✅ |
| Cost circuit breaker | 每副本只看自己那片花費，永遠不跳閘 | `cost_circuit_state()` 已讀 redis 共享 micro-dollar 計數 ✅ |

**已實作部分**：`check_quotas` 的 redis 路徑用 `_RESERVE_LUA`
（`GET + 比較 + INCRBY` 單次 server-side 原子），`record_usage` 用 `INCRBY` 對帳，
`cost_circuit_state` 讀 `cost:daily:<day>` 共享計數。**這部分跨副本已正確。**

**缺口（待補）**：`check_rpm` / `check_login_rpm` 的 token bucket **仍是 in-memory**
（`_user_rpm` / `_login_ip_rpm` dict + `_STATE_LOCK`）。多副本下 RPM 上限會被放大 N 倍。

> **改哪裡**：在 `rate_limit.py` 加一條 redis token-bucket（典型作法：
> 用 Lua 實作「sliding window log」或「token bucket with `HSET tokens/last` + `EVAL`」）。
> 模式跟 `_RESERVE_LUA` 完全一致——把 refill+consume 放進一個 `EVAL`。
> **待查證**：是否直接採用 `redis-cell`（`CL.THROTTLE`，GCRA 演算法的 redis module）
> 以避免自寫 Lua；取決於營運是否願意裝 module。

### 2.4 Cache 一致性

`cache.py` 的 `_MemoryCache` 是**每副本各一份**——這在 cache 語意下**不是正確性問題、
是命中率問題**：副本 A 算過的回應，副本 B 會 miss 再算一次（多花一次 LLM 錢）。
切 `CACHE_BACKEND=redis`（`redis_cache.py`，已實作 graceful degradation + JSON 序列化）
後，全副本共享命中。

**注意 cache key 的隔離不變量**（Q9，§9 of CLAUDE.md「Don't cache responses cross-user」）：
`response_cache_key` 強制帶 `tenant:user:case`，`embedding_cache_key` 折入 `tenant_id`（H-3）。
**切 redis 後這些不變量自動保持**——因為隔離靠 key 命名，不靠後端。

> **per-tenant 容量上限 (M-8)**：in-memory 版有 `MAX_CACHE_ENTRIES_PER_TENANT` FIFO 驅逐。
> 切 redis 後要靠 redis 的 `maxmemory-policy allkeys-lru` + key 前綴 quota 近似——
> **待查證**：redis 沒有原生 per-prefix 容量上限，可能需要 per-tenant 獨立 redis logical DB
> 或 key 數量的週期性巡檢。POC 規模可先不做。

### 2.5 ai_engine 擴展：無狀態，但要管 GPU 與下游一致

ai_engine 自身無狀態，加副本零顧慮。要注意的是它的下游：

- **Qdrant 連線**：所有 ai_engine 副本指向同一個 Qdrant 叢集端點（不是各自 in-memory store）。
  確保 `VECTOR_BACKEND=qdrant`、`QDRANT_URL` 指向叢集 VIP / service。
- **LLM 池**：mock/anthropic 模式無狀態；`local`(Ollama) / `dify` 模式綁 GPU，
  副本數受 GPU 數量限制。雲端 anthropic 路徑可隨意擴；地端路徑按 GPU 卡數擴。
- **embedding cache**：`bge-m3` 模式下，embedding 是確定性的，可全副本共享 redis cache。

## 3. 機密性驅動的分散式拓樸（重點）

這是 PatentMind 與一般 SaaS 最大的差異。**拓樸不是為了擴展，是為了把資料釘在合規邊界內。**

### 3.1 核心原則：信任域切割

```
═══════════════════════════════════════════════════════════════════════
  雲端控制平面 (Cloud Control Plane)         ← 非機密案的彈性運算 + 統一管理
═══════════════════════════════════════════════════════════════════════
   ┌────────────┐   ┌──────────────┐   ┌─────────────────────────────┐
   │ 管理面板    │   │ 非機密 gateway│   │ Anthropic / 雲端大模型      │
   │ 計費/配額   │   │ + ai_engine   │──►│ （只收 redacted retrieval） │
   │ 全域稽核驗證 │   │  彈性多副本   │   └─────────────────────────────┘
   └────────────┘   └──────────────┘
          ▲                                       ▲
          │ 只傳「稽核 Merkle root + 計量」          │ 只傳 redacted 文字 (Q3 egress guard)
══════════╪═══════════════════════════════════════╪════════════════════════
  地端資料平面 A (事務所甲機房)  │  地端資料平面 B (事務所乙 / 分所)
══════════╪═══════════════════════════════════════╪════════════════════════
   ┌──────┴───────┐                         ┌──────┴───────┐
   │ gateway(地)   │  機密案永不離機         │ gateway(地)   │
   │ ai_engine(地) │ ─┐                      │ ai_engine(地) │
   │ Ollama GPU    │  │ 不變量 #7            │ Ollama GPU    │
   │ Qdrant(甲)    │  │ confidential/        │ Qdrant(乙)    │
   │ Postgres(甲)  │  │ top_secret           │ Postgres(乙)  │
   │ MaskingStore  │  │ → 地端 LLM           │ MaskingStore  │
   │ MinIO WORM(甲)│ ◄┘                      │ MinIO WORM(乙)│
   └──────────────┘                         └──────────────┘
```

**信任域切割規則**：

1. **機密案 (confidential / top_secret)**：整條鏈在地端機房內完成。
   gateway → ai_engine → Ollama 全部地端，向量在地端 Qdrant，
   稽核寫地端 Postgres，WORM 封到地端 MinIO。**沒有任何 byte 離開機房。**
   技術強制點：`route_model`（不變量 #7，`LOCAL_LLM_FOR_SECURITY_LEVELS`）
   + Q3 egress guard（`EGRESS_GUARD_ENABLED`，掃描 outbound 字串攔未遮罩 PII）。

2. **非機密案**：原文留地端（Q3），但**經 redaction 後**的 retrieval 結果
   可出機房打雲端 Anthropic（品質較好）。redaction 是強制的（不變量 #3）。

3. **跨邊界只允許兩種資料流**：
   (a) 地端 → 雲端：**redacted 文字**（egress guard 把關）。
   (b) 地端 → 雲端：**稽核摘要**（Merkle root + token 計量），給中央計費與全域驗證——
   **不含案件內容**（見 §4）。

### 3.2 資料落地 / 落境邊界 (data residency)

| 資料類型 | 允許落地範圍 | 強制機制 |
|----------|--------------|----------|
| 機密案原文 / OA PDF | **只在該所地端機房** | 不變量 #7 路由 + egress guard |
| 可逆遮罩 mapping table | **只在 on-prem**（`MAPPING_DB_PATH` 在 `data/`） | §9 of CLAUDE.md；絕不集中化 |
| 機密案向量 | 地端 Qdrant collection | per-tenant collection + 地端部署 |
| 非機密 redacted retrieval | 可上雲 | Q3 hybrid + egress guard |
| 稽核列（內容 hash） | 地端 Postgres（內容只存 hash，不存原文） | audit schema 只存 `request_hash`/`response_hash` |
| 稽核 Merkle root | 可上雲（給全域驗證） | 段鏈 manifest |

> **關鍵洞察**：audit schema **本來就只存 hash 不存原文**
> （`audit.py:_DDL` 的 `request_hash`/`response_hash`）。這讓「稽核摘要上雲做全域驗證」
> 在隱私上是安全的——中央拿到 hash 鏈能驗完整性，但還原不出案件內容。
> **這是現有設計給分散式架構留的一個漂亮後門。**

### 3.3 Air-gap（實體隔離網）部署選項

某些頂級事務所或政府專利案要求**完全離網 (air-gapped)**。PatentMind 的 hybrid 設計
讓這變成一個 **knob 組合**，而非重寫：

- `LLM_MODE=local`（或 `dify` → 地端 Ollama），**禁用 anthropic 路徑**。
- `DIFY_EGRESS_LOCAL=true`（否則 `-CONF` 案硬拒，見 Q3）。
- 所有 `*_BACKEND` 指向地端基礎設施；無任何雲端端點。
- 管理面板與全域驗證**改為離線匯出**（USB/單向資料閘）而非雲端回傳。

> **air-gap 模式 = 把「地端資料平面」整套搬進隔離網，移除所有跨邊界資料流。**
> 代價：失去雲端大模型品質（只剩 qwen2.5:7b 級地端模型）與即時中央計費。
> 這是合規與品質的取捨，由客戶簽。

### 3.4 Per-tenant 資料隔離（既有，要在分散式下保持）

PatentMind 採 **single-tenant data + multi-tenant control**（Q5）——物理隔離，不是邏輯 tenant_id。
分散式化時這條**只能加強不能放鬆**：

| 隔離面 | 現有機制 | 分散式下注意 |
|--------|----------|--------------|
| 向量 | Qdrant per-tenant collection（`rag.py:_coll(tenant_id)`） | 叢集 sharding 後仍 per-tenant collection；見 §6.2 collection 數量問題 |
| 遮罩詞庫 | `data/tenant_dicts/<tenant_id>.json` | 多副本要共享/同步這些檔（或外推到 redis/物件儲存） |
| 稽核鏈 | audit row 帶 `tenant_id`，`list_for_tenant` 強制 filter | per-tenant 分鏈是分散式正解（§4.3） |
| cache | key 帶 tenant（`response_cache_key` / `embedding_cache_key`） | 切 redis 後 key 隔離自動保持 |
| quota | `(tenant_id, YYYY-MM)` keyed | redis key 已帶 tenant |

> 全域驗證已有 `verify_global_chain` 的 **tenant 白名單檢查**——任何
> `tenant_id` 不在 `DEMO_TENANTS` 的列會被標 `unknown_tenant`，
> 抓「被 DBA 偷塞的幽靈租戶 / typo 租戶」。`verify_cross_tenant` 還會抓
> **跨租戶 row_hash 碰撞**（複製注入的徵兆）。這些在分散式下是中央稽核的核心工具。

## 4. 多分所 / 多地點

### 4.1 場景

- **一所多分所**（台北所 / 新竹所 / 美國分所）：同一租戶，但不同地理位置，
  各自有當地資料就近需求，且可能有當地法遵（美國分所資料不可回台）。
- **多所一平台**（SaaS）：不同事務所共用控制平面，但資料絕對隔離。

這兩者疊加後，需求是：**資料就近 (data locality) + 跨所/跨分所協作但案件隔離 + 稽核可全域驗證**。

### 4.2 資料就近與跨所協作

```
        中央控制平面 (雲端)
        ├─ 管理面板 / 計費
        └─ 全域稽核驗證 (verify-only, 不 write)
               ▲              ▲              ▲
   Merkle root │   Merkle root│  Merkle root │
        ┌──────┴────┐  ┌──────┴────┐  ┌──────┴────┐
        │ 台北所機房 │  │ 新竹所機房 │  │ 美國分所   │
        │ 完整資料平面│  │ 完整資料平面│  │ 完整資料平面│
        └───────────┘  └───────────┘  └───────────┘
         案件就近處理     案件就近處理      案件不出境
```

- **資料就近**：每個地點一套完整地端資料平面，案件在產生地就近處理，
  延遲低、且滿足當地落境要求（美國分所案件不回台）。
- **跨所協作但案件隔離**：協作透過**控制平面授權 + magic link**（Q12）——
  甲所律師被授權看乙所某案進度時，走的是**經授權的 case ACL**
  （`authorize_case_access`，不變量 #6），而非把資料複製過去。
  案件資料**留在原機房**，只是 ACL 開了一道門。

### 4.3 稽核鏈的分散與全域驗證（核心難題）

現況：audit chain 是 **per-tenant** 的（§7 pitfall #4 of CLAUDE.md），
但**實體上是單一全域鏈**（`_last_row_hash` 不分租戶，所以乙租戶某列的 `prev`
可能指向甲租戶的 `row_hash`——`verify_global_chain` 正是為此存在）。

多分所/多地點下，**不能讓所有地點寫進同一條全域鏈**——那需要跨地網路同步寫入，
延遲與可用性都不可接受，也違背資料就近。**正解是分鏈**：

| 方案 | 描述 | 優點 | 缺點 |
|------|------|------|------|
| **A. per-tenant 分鏈** | 每租戶一條獨立 hash chain（`prev` 只在同租戶內鏈） | 租戶可獨立驗、獨立封存；天然契合資料就近 | 失去跨租戶單鏈的「全域插入序」證據；需改 `_last_row_hash` 為 tenant-scoped |
| **B. per-location 分鏈** | 每機房一條鏈，租戶資料可能跨多鏈 | 契合資料就近 | 跨機房的同租戶稽核需合併驗證 |
| **C. 維持全域單鏈** | 現況 | 最強的全域順序證據 | 跨地寫入同步不可行 |

> **建議**：採 **A（per-tenant 分鏈）**，理由是它同時解決「資料就近」與「租戶隔離」，
> 且與 Q5 single-tenant 物理隔離哲學一致。
> **改哪裡**：`audit.py:_last_row_hash` / `write` 把 prev 查詢改成
> `WHERE tenant_id = ?`（或更乾脆——每租戶一張 audit 表 / 一個 schema），
> 然後 `verify_chain(tenant_id)` 變成各租戶的權威驗證（它已經是 tenant-scoped 的）。
> `verify_global_chain` 的角色轉為**中央離線稽核**：收集各地端傳來的
> Merkle root + 段鏈 manifest，驗每條 per-tenant 鏈的完整性與連續性。

**全域驗證流程（分散式）**：

```
各地端 ──(週期/每封段)──► 上傳 segment manifest（Merkle root + audit_id 範圍）
                                  │  只含 hash，不含內容（§3.2）
                                  ▼
                        中央稽核服務 verify-only
                        ├─ 重算每段 Merkle root（信 nothing）
                        ├─ 驗段鏈連續性（prev_root linkage + offset 連續）
                        └─ 跨租戶碰撞檢查（verify_cross_tenant）
```

這正是 `audit_archive.py:verify_archive` 已經實作的三層檢查
（重算 Merkle root / 段鏈連續 / 對活庫 row_hash 交叉比對），
只是把「活庫交叉比對」那層移到地端做、中央只做前兩層 + 跨租戶碰撞。

### 4.4 WORM 封存的分散式一致性

每個地端各自封存到**當地 MinIO**（資料就近 + 不離境）。一致性要點：

- **段鏈自洽 (self-consistent per location)**：`audit_archive.py` 的段鏈是
  per-archive 的 Merkle 鏈（每段 `prev_root` 指前段 root）。每個地端各跑一條，自洽。
- **高水位 (high-water mark) 是 per-archive 的** `_state.json`——不需跨地協調。
- **冪等封段**：`seal_next_segment` 已對「段已存在」做 refuse-to-overwrite，
  cron 重跑安全。多地各自 cron 互不干擾。
- **中央只收 manifest 不收資料**：滿足落境（封存資料留地端 MinIO），
  中央能驗鏈完整性（manifest 含 Merkle root）。

## 5. 可靠性與一致性

### 5.1 Audit：exactly-once 稽核（已做對，分散式下要小心）

`audit_outbox.py` 已實作 **write-ahead outbox** 補足不變量 #4：
主庫寫失敗 → `enqueue` 寫一行 JSONL + `fsync`（schema-less / lock-free / 最耐久）；
`replay_outbox` 待 DB 恢復後重放，並用「成功即從檔移除」保證**不重複寫**（冪等）。

**分散式注意**：

- **outbox 是 per-replica 本機檔**（`AUDIT_OUTBOX_PATH`）。每個 gateway 副本
  各有一份 outbox，需**各自 replay**。副本若整機掛掉，那份 outbox 要能被
  接手（共享卷 / 或 outbox 也外推到 redis stream / DB）。
  **待補**：副本不可恢復時的 outbox 接管策略。
- **replay 冪等性依賴「成功即移除」**——這在單副本對單 DB 時正確；
  多副本同時 replay 各自的 outbox 到同一 DB 沒問題（各寫各的新列）。

### 5.2 Hash chain 的順序保證（分散式最硬的一致性問題）

現況：`write` 在 `RLock` 下做「讀 prev → 算 hash → insert」，**單進程序列化**。
**多副本並發寫同一條鏈會分叉**（兩副本都讀到同一個 prev，各自接一列）。

| 方案 | 做法 | 評估 |
|------|------|------|
| **A. per-tenant 分鏈 + 單寫入點** | 每租戶資料平面在地端，該租戶只有一個 gateway 寫入點 | 與 §4.3 一致；最簡單；推薦 |
| **B. DB 端原子化 chain** | 把「取 prev + insert」做成單一 SQL（如 `INSERT ... SELECT row_hash FROM audit ORDER BY row_seq DESC LIMIT 1`）+ 序列化隔離級別 | 跨副本安全；需 Postgres `SERIALIZABLE` 或顯式 `SELECT ... FOR UPDATE` 鎖一個 sentinel 列 |
| **C. 單一 audit-writer 服務** | 所有副本把稽核列丟一個專責 writer（佇列），由它序列化寫 | 集中順序保證；但 audit writer 變單點，需自己的 HA |

> **建議**：地端單寫入點場景用 **A**；若一個信任域內真的有多 gateway 副本同寫一鏈，
> 用 **B**（Postgres 端鎖一個 per-tenant sentinel 列，把「取 prev → insert」變原子）。
> **待查證**：Postgres `SERIALIZABLE` 在高並發稽核寫入下的吞吐衰減，需壓測。

### 5.3 備援與 DR：snapshot vs streaming replication 的 RPO 缺口

現況 `backup.py`：snapshot / restore / **DR drill**（restore 後驗 audit chain）/ GDPR erasure，
排程走 `scripts/run_backup.py` + `backup_cron.sh` + schtasks。

**已知缺口（CLAUDE.md §3b 明列）**：snapshot cron 的 **RPO 達不到 < 5 分鐘**——
兩次 snapshot 之間崩潰，會丟失這段時間的稽核列。對律師責任險/合規而言，
**丟稽核列是合約終止級缺陷**。

| 機制 | RPO | RTO | 適用 |
|------|-----|-----|------|
| 每日 snapshot（POC 現況） | ~24h | 慢 | POC only，**不可上 prod** |
| 每小時 snapshot + cron | ~1h | 中 | 過渡 |
| **Postgres streaming replication** | **近 0**（async ~< 1MB；sync = 0） | ~30–45s（Patroni 自動 failover） | **生產目標** |

> **建議**：audit Postgres 上 **Patroni + etcd + streaming replication**。
> 依研究，Patroni 預設 async 配置 RPO < 1MB、RTO ≈ 45s；
> 若 audit 要求**零丟失**，開 synchronous_commit（代價 +2~5ms 寫延遲，
> 但稽核寫在 LLM 熱路徑之外，可接受）。
> **WORM 是第二道保險**：即使 Postgres 丟了未複製的尾段，那些列若已封進 MinIO
> Object Lock，仍可從 WORM 還原——這是 audit + WORM 雙寫的價值。
> **改哪裡（CLAUDE.md §3b 提示）**：postgres 模式的備份要從
> `backup.py` 的 SQLite 檔快照，改走 `pg_dump` / streaming replication；
> `quality_eval.py` 的離線讀取也要對齊 postgres。

### 5.4 各狀態後端的一致性語意

| 後端 | 一致性需求 | 故障時策略 |
|------|------------|-----------|
| Postgres audit | 強一致（不可丟列） | fail-loud（`PostgresAuditWriter` 連不上**拒絕開機**——「寧可無服務也不要無稽核」）→ 寫失敗落 outbox |
| Redis quota | 強一致（不可超賣） | `RATE_LIMIT_REDIS_DEGRADE=closed`（預設）→ 連不上時 reject（fail-closed，配額是花費保護） |
| Redis cache | 最終一致即可（軟） | graceful degrade → miss 退回算（不擋請求） |
| Redis revocation | 強一致（撤銷不可漏） | fail-closed 傾向（撤銷漏 = 安全風險），短 timeout 快速失敗 |
| Qdrant | 最終一致可接受（檢索） | 叢集 Raft；replica 故障可降級查 |
| MinIO WORM | 強一致 + 不可變 | erasure coding 容多盤/多節點故障 |

> 注意 redis 的故障策略**不是一刀切**：quota/revocation fail-closed（安全優先），
> cache fail-open（可用性優先）。這個區分已在現有碼裡（`RATE_LIMIT_REDIS_DEGRADE`
> vs `redis_cache` 的 graceful degrade），分散式下要保持。

## 6. 部署形態：compose → Kubernetes

### 6.1 現況：單機 docker-compose

`start_delivery.sh` 起 qdrant :6333 / redis :6379 / postgres :15432 / MinIO :19000
+ 三個 process + probe digiRunner :18080 與 Dify :8088。**單機、單副本、無 HA。**
適合 demo / 交付驗證，不適合生產。

### 6.2 有狀態服務的生產級營運

#### Postgres HA（audit）
- **Patroni + etcd（3 節點）+ streaming replication**。Patroni 管 failover/leader election，
  etcd 做分散式共識儲存。預設 RTO ≈ 45s、RPO < 1MB；要零丟失開 synchronous_commit。
- K8s 上可用 Patroni 官方模板或 CloudNativePG operator（**待查證**：選型）。

#### Qdrant 叢集（向量）
- **3+ 節點、replication factor ≥ 2、每節點至少一 shard/replica**，Raft 共識同步。
  「resilience 最重要」的生產建議是 3+ 節點 + 2+ shard replica，可在單節點掛時持續服務。
- 啟用方式：`QDRANT__CLUSTER__ENABLED=true`（或 Helm chart 設 replica count + replication factor）。
- **per-tenant collection 的擴展性風險**：Q5 每租戶一 collection，租戶多時 collection 數量爆炸。
  **待查證**：Qdrant 大量 collection 的記憶體/開銷上限；替代方案是
  **單 collection + tenant payload 分區 + 自訂 sharding**（Qdrant 官方有 multi-tenancy 模式），
  但這跟 Q5「物理隔離」哲學有張力——需評估「物理隔離 vs collection 數量」取捨。

#### Redis HA（cache/quota/revocation）
- **Sentinel** 對 PatentMind 是更合適的選擇：資料集小（計數器 + cache，遠 < 100GB），
  需要的是**高可用 + 自動 failover**，不是水平分片吞吐。
  Sentinel 簡單、覆蓋 95% 場景；Cluster 是為了水平擴展寫吞吐才需要，且改變 multi-key 語意、
  需 cluster-aware client——對我們是過度設計。
- **選 Sentinel**，除非未來計數器/cache 量級超過單節點記憶體（屆時再評估 Cluster）。
- **待查證**：Lua `EVAL`（quota reserve）在 Sentinel 容錯切換時的行為——
  failover 期間的 in-flight EVAL 處理。

#### MinIO 分散式（WORM）
- **分散模式 + erasure coding**（預設 12 data + 4 parity 的 erasure set），
  最低 2 盤啟用，可容多盤/多節點故障 + bit-rot 防護。
- Object Lock（WORM）已被 Cohasset 認證符合 SEC 17a-4(f)/FINRA 4511(C)/CFTC 1.31——
  對律所/合規場景是現成的法遵保存方案。
- K8s 上用 spread zones 把 data/parity shard 分散到不同 failure domain（機架/可用區）。
- **生產用 COMPLIANCE 模式前**確認法遵保存期（7 年，Q13）——COMPLIANCE 一旦設定**不可逆**。

### 6.3 無狀態服務在 K8s

- gateway / ai_engine 做成 `Deployment` + HPA（依 CPU / 自訂 LLM 佇列深度指標伸縮）。
- ai_engine 地端 LLM 副本綁 GPU node（`nodeSelector` / GPU resource request）。
- **機密案的 K8s 隔離**：地端資料平面用獨立 namespace / 獨立叢集，
  NetworkPolicy 禁止機密 namespace egress 到雲端（air-gap 的 K8s 版）。

### 6.4 K8s 拓樸全圖

```
┌─────────────────────── 雲端 K8s（控制平面 + 非機密資料平面）──────────────────┐
│  Ingress ─► gateway Deployment (HPA) ─► ai_engine Deployment (HPA, 雲端 LLM)  │
│              │                              │                                  │
│       Redis Sentinel(3)            Anthropic API (egress, redacted only)       │
│       Postgres Patroni(3) ◄─ 中央稽核驗證 (verify-only)                        │

                  ▲ Merkle root + 計量（hash only）
══════════════════╪══════════════════ 信任域邊界 ═══════════════════════════════
┌────────── 地端 K8s / 單機（每事務所 / 每分所）─ NetworkPolicy: no cloud egress ┐
```

## 7. 落地路線圖

原則：**每階段先切後端、再上 HA、最後拆信任域**，且每步都驗
`verify.sh`（不變量未破）。

### 階段 0 — 現況（POC / 交付驗證）
- **狀態**：單機 compose，多數 `*_BACKEND` 可選 redis/postgres/qdrant/s3，但跑 demo 時多為單副本。
- **不變量**：全綠（`verify.sh`）。

### 階段 1 — 共享狀態後端（讓運算層真正可多副本）
| 改動點 | 效益 | 風險 | 不變量相容性 |
|--------|------|------|--------------|
| 全面切 `RATE_LIMIT_BACKEND=redis` / `CACHE_BACKEND=redis` / `REVOCATION_BACKEND=redis` | 多副本下 quota 不超賣、cache 共享、撤銷一致 | redis 單點故障擋請求（fail-closed） | #8（quota 前置）保持——redis Lua 已原子 |
| **補 RPM token bucket 的 redis 化**（`check_rpm`/`check_login_rpm`） | RPM 上限不被副本數放大 | 自寫 Lua 或裝 redis-cell | 限流仍在 handler try/finally 內（#4） |
| 外推 `tenant_dicts` 到共享儲存（或啟動同步） | 多副本遮罩詞庫一致 | 詞庫 reload 時序 | #3 redaction 保持 |
| **不要**集中化 MaskingStore | — | — | §9「mapping 不離 on-prem」 |

**驗收**：起 2 個 gateway 副本 + LB，跑配額超賣壓測（並發 reserve 不超 cap）、
logout token 在另一副本被拒。

### 階段 2 — 有狀態服務 HA
| 改動點 | 效益 | 風險 | 不變量相容性 |
|--------|------|------|--------------|
| Postgres → Patroni + streaming replication | audit RPO 從 ~24h 降到近 0；RTO ~45s | failover 期間短暫寫拒（落 outbox） | #4：outbox 補；fail-loud 不變 |
| `backup.py` 改 `pg_dump`/replication（取代 SQLite 快照） | 備份對齊 postgres 模式 | 遷移期雙軌 | audit chain 驗證不變 |
| Redis Sentinel(3) | cache/quota HA | failover 期 EVAL 行為（待查證） | quota 一致性保持 |
| Qdrant 叢集(3, RF≥2) | 檢索 HA + 可擴 | per-tenant collection 數量風險 | per-tenant 隔離保持 |
| MinIO 分散 erasure(4 node) | WORM 高可用 + bit-rot 防護 | COMPLIANCE 不可逆 | WORM 段鏈保持 |

**驗收**：殺主 Postgres 節點觀察 failover + audit chain 仍 verify；
殺一 Qdrant 節點檢索仍服務；DR drill（restore + 驗鏈）通過。

### 階段 3 — 拆信任域（機密性拓樸 + 多地點）
| 改動點 | 效益 | 風險 | 不變量相容性 |
|--------|------|------|--------------|
| 雲端控制平面 + 地端資料平面分離 | 機密案永不離機；資料就近 | 跨邊界資料流治理複雜 | #7 路由 + Q3 egress 強制 |
| audit chain 改 **per-tenant 分鏈** | 跨地不需同步寫；租戶獨立驗 | 改 `_last_row_hash` 為 tenant-scoped；失去全域插入序 | #4 保持（per-tenant 一鏈一列序）；隔離加強 |
| 中央稽核改 **verify-only**（收 manifest 不收內容） | 全域驗證但不破落境 | 中央驗證延遲（週期性） | 內容只存 hash（既有） |
| 各地端各自封 WORM 到當地 MinIO | 落境合規 | 多地 cron 營運 | 段鏈各自自洽 |
| K8s NetworkPolicy 鎖機密 namespace egress | air-gap 化選項 | 失去雲端大模型品質 | #7 強制 |

**驗收**：機密案（`-CONF`）全鏈不離地端機房（網路抓包驗無 egress）；
中央用 manifest 驗各地 per-tenant 鏈完整；跨所協作走 ACL 不複製資料。

### 階段 4 — air-gap 交付選項（特定客戶）
- 整套地端資料平面進隔離網，移除所有跨邊界流。
- 全域驗證改離線匯出（單向資料閘）。
- `LLM_MODE=local` only，無雲端端點。
