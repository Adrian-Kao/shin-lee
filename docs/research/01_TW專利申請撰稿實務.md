## 0. 30 秒摘要

**這份在講什麼**：台灣一件「發明專利」從委託到送件的完整工作流，每一步專利師做什麼決策、卡在哪，以及這些步驟如何對映到資料模型與 PatentMind 現有模組。

**最關鍵的 3 個 takeaway（對系統設計）**：

1. **「說明書 ↔ 請求項」的支持關係是整個資料模型的骨架。** 台灣專利法 §26 要求「請求項必須為說明書所支持」「可據以實現」。這不是排版問題，而是一個可被機器檢查的**圖（graph）**：每個 claim 的每個技術特徵，都必須能在說明書找到對應揭露。AI 最大的價值之一就是維護並檢查這張圖（對映 `element_table.py` 的數字對應、`claim_tree.py` 的依附關係，未來可擴成「特徵→說明書段落」支持度檢查）。

2. **撰稿是「結構化生成 + 一致性約束」問題，不是自由寫作。** 請求項用語必須前後一致（先行詞 / antecedent basis）、上下位佈局必須有層次、claim 與說明書術語必須對齊。這些都是**確定性可檢查的約束**，正是 AI 該扛的部分（草稿生成 + 一致性 lint）。本 repo 已用純 regex 做 claim 依附與 element table，正是「能用確定性就不要丟 LLM」的範例。

3. **簽核責任在專利師，AI 永遠是輔助。** 撰稿牽涉「claim 範圍拿捏」「先前技術判斷」「禁反言風險」——這些決定專利的生死與訴訟價值，法律責任在署名的專利師身上。系統必須是 **draft → 人類審閱 → 簽核** 的流程，對映 PatentMind 的設計不變量（Q14 verifier 硬牆、Q16 sign-off / provenance、「Don't skip the verifier」）。**絕不能讓 AI 自動送件。**

## 1. 台灣三種專利：差異與審查路徑

台灣專利法把「專利」分成三種，**保護標的、審查方式、撰稿產出物都不同**。對工程師而言，最重要的是「審查路徑不同」會決定系統要支援哪些 workflow 與時程模型。

| 維度 | 發明專利 (Invention) | 新型專利 (Utility Model) | 設計專利 (Design) |
|---|---|---|---|
| 保護標的 | 利用自然法則之技術思想之**創作**（方法、物、用途皆可）法 §21 | 對物品之**形狀、構造或組合**之創作（只保護「有形物品結構」，不含方法）法 §104 | 對物品**全部或部分之形狀、花紋、色彩或其結合，透過視覺訴求之創作**；含電腦圖像(icon)與 GUI 法 §121 |
| 審查方式 | **實體審查**（須請求，逐項判斷新穎性/進步性/可實施性等） | **形式審查**（只看有無明顯不符形式要件，不查新穎/進步性）法 §112 | **實體審查**（逐件審查，含近似判斷） |
| 是否需另請求審查 | **要**：申請日起 **3 年內**須請求實體審查，逾期視為撤回 法 §38 | 不需（形式審查，核准後想主張權利才另請「技術報告」） | 不需（直接進實體審查） |
| 核准後的「品質背書」 | 已經實體審查，權利相對穩固 | **核准 ≠ 有效**。要行使權利前應先取得**新型專利技術報告**（§115），否則行使權利後被撤銷可能要負損賠 | 已實體審查 |
| 早期公開 | 自申請日次日起 **18 個月**早期公開（不論審查是否完成）法 §37 | 無早期公開（形式審查、核准即公告） | 無早期公開 |
| 權利期間 | 申請日起 **20 年** | 申請日起 **10 年** | 申請日起 **15 年**（衍生設計同母案屆滿日）|
| 撰稿產出物 | 說明書 + 申請專利範圍(claims) + 摘要 + 圖式 | 說明書 + claims + 摘要 + 圖式（**圖式幾乎必備**，因保護結構） | **圖式為核心**（六面視圖等）+ 設計名稱 + 物品用途/設計說明，**無 claim** |

> **新型 vs 發明 的工程含義**：新型走形式審查，TIPO 不主動查前案，所以「核准」訊號弱。系統若要對新型做風險提示，重點是**新型技術報告**（代碼 1–6 的比對結果，代碼 6 = 查無足以否定的前案 = 較強）。發明走實體審查，會收到「審查意見通知函（Office Action）」，這才是 PatentMind OA 分析模組的主戰場。

> **設計專利的工程含義**：設計**沒有 claim 文字**，保護範圍由**圖式**界定。`claim_tree.py` / `element_table.py` 對設計案幾乎不適用；設計案是 vision/圖像比對問題（與本 repo 的 Q8 figure 路線相關，但目前模組是文字導向）。**本文件其餘部分聚焦發明專利**（PatentMind 的主場景）。

## 2. 一件發明專利：從委託到送件的完整流程

下面是「事務所專利師」收到發明人/客戶委託後的真實工作流。每一步標出 **專利師做什麼決策、典型耗時、卡點**，以及 **資料模型含義**。

```
委託/交底  →  前案檢索  →  專利性評估  →  claim 佈局  →  說明書撰稿  →  圖式  →  摘要  →  內外部審閱  →  送件
(交底會)     (search)     (patentability)  (claim strategy) (spec drafting) (drawings) (abstract) (review)    (filing)
```

### 步驟 2.1 — 技術揭露 / 交底（Invention Disclosure）

- **做什麼**：與發明人開交底會，理解「發明真正解決什麼問題、與既有作法差在哪、最廣可以主張到哪、最窄的可實施範例是什麼」。發明人通常給的是「產品/實作」，專利師要抽象成「技術思想」。
- **決策**：發明的**核心發明點（inventive concept）**是什麼？哪些是必要技術特徵、哪些是 optional？
- **耗時**：0.5–2 小時會議 + 數小時消化。
- **卡點**：發明人講的是「我做的東西」，不是「我能獨佔的範圍」。發明人常**過度揭露細節**（不利最廣 claim）或**講不清楚差異點**。技術領域跨度大時專利師要快速補背景知識。
- **資料模型含義**：產出一份半結構化的「交底表」——`{problem, prior_approach, inventive_concept, essential_features[], optional_features[], embodiments[]}`。這是後續所有產物的 source of truth。

### 步驟 2.2 — 先前技術檢索（Prior Art Search）

- **做什麼**：用關鍵字 / 分類號（IPC/CPC）/ 引用關係，在 TIPO 專利檢索、Google Patents、USPTO、EPO Espacenet 等檢索最接近的前案（closest prior art）。
- **決策**：哪幾件是「最接近前案」？發明點是否已被揭露？要不要調整 claim 範圍迴避前案？
- **耗時**：2–8 小時（視技術領域擁擠程度）。
- **卡點**：**查得不夠是最大隱患**——漏掉關鍵前案，會在審查階段（甚至訴訟階段）才爆出來，且為時已晚。關鍵字選擇、同義詞、跨語言（中/英/日）都影響召回率。
- **資料模型含義**：產出 `prior_art[] = {patent_no, relevance, overlapping_features[], source}`。這對映 PatentMind 的 RAG（Q6/Q7，`rag.py` per-tenant Qdrant collection）與 grounded set 概念——**檢索到的前案＝後續 grounding 的來源**。

### 步驟 2.3 — 專利性評估（Patentability Assessment）

- **做什麼**：對照前案判斷**新穎性（§22-1）、進步性（§22-2，「所屬技術領域具通常知識者能否輕易完成」）、產業利用性（§22 序）**，給客戶 go/no-go 建議與「能拿到多寬」的預期。
- **決策**：值不值得申請？以什麼角度（哪個發明點）切入最穩？
- **耗時**：1–4 小時 + 報告撰寫。
- **卡點**：進步性是**最主觀**的判斷，事務所內部常有分歧。「能拿多寬」要兼顧客戶商業目的。
- **資料模型含義**：這是「判斷」而非「生成」，**法律責任高、AI 只能輔助比對不能下結論**（見 §6）。

### 步驟 2.4 — 請求項佈局（Claim Strategy / Drafting）

- **做什麼**：設計 claim 結構——最廣的獨立項、逐層收斂的附屬項、不同範疇（category）的獨立項（物 + 方法 + 用途 + 系統）。
- **決策**：獨立項寫多廣（廣＝易被前案打到、易無效；窄＝易迴避、價值低）？附屬項層次怎麼鋪（為答辯預留「退路」）？要不要多重附屬？單一性（§33）有沒有問題？
- **耗時**：數小時——這是**最耗腦力、最決定專利價值**的一步。
- **卡點**：**範圍拿捏（claim breadth）的拉扯**——廣窄之間沒有標準答案，是經驗活。
- **資料模型含義**：產出一棵 claim tree（對映 `claim_tree.py`：`{claim_no, depends_on, parents[], is_independent, depth}`）。**這是 PatentMind 已實作的結構**。詳見 §4。

### 步驟 2.5 — 說明書撰稿（Specification Drafting）

- **做什麼**：依施行細則 §17 規定的法定結構撰寫（見 §3）。核心是：讓 claim 的**每個技術特徵都在說明書「實施方式」找得到對應揭露**（為了 §26「可據以實現」與「為說明書所支持」），同時鋪陳「先前技術 → 所欲解決問題 → 技術手段 → 功效」的因果鏈以支撐進步性。
- **決策**：實施例要寫幾個（多＝支持度高但耗時、可能過度揭露）？用語怎麼定（一旦定了全文要一致）？
- **耗時**：**最大時間黑洞，一件中等複雜度發明案 8–20+ 工時**。
- **卡點**：**用語一致性**（同一元件全文同名、claim 與 spec 同名）、**支持度**（claim 寫了 spec 沒揭露＝§26 瑕疵）、**翻譯**（很多案要中英雙語）。
- **資料模型含義**：說明書是一份**有法定章節結構的文件**，且與 claim tree、element table（reference numerals）有**強交叉引用關係**。詳見 §3、§5、§6。

### 步驟 2.6 — 圖式（Drawings）

- **做什麼**：準備圖式，元件標上**參考符號（reference numerals）**，符號要與說明書「符號說明」與內文一致。
- **卡點**：符號不一致（圖上有 10，說明書沒解釋 10）是常見退件理由。
- **資料模型含義**：對映 `element_table.py`——把「`基板 10`、`第一電極 102`」這類「描述 + 數字」抽成 `{numeral: description}` 表，並可在「本案 ↔ 引證案」之間做 `correlate()` 數字對應。這是 OA 答辯時「本案元件 102 對應引證案元件 200」推理的基礎。

### 步驟 2.7 — 摘要（Abstract）

- **做什麼**：寫 ~200 字摘要，**注意**：摘要法律上**不得用來解釋專利權範圍、不得作為判斷揭露是否充分的依據**（法 §26-3 / 施行細則）。純檢索用。
- **資料模型含義**：低風險、樣板化，AI 可生成草稿。

### 步驟 2.8 — 審閱與送件（Review & Filing）

- **做什麼**：資深專利師/合夥人審閱 claim 範圍與 spec 一致性 → 客戶確認 → 線上送件（TIPO 電子申請）。
- **資料模型含義**：**簽核（sign-off）是責任轉移點**——對映 PatentMind 的 Q16 signoff / provenance。送件後才開始跑審查時程（§38 三年內請求實審、§37 十八個月公開、後續 OA 答辯期間）。

> **時程模型備註**：送件後的官方期限（OA 答辯指定期間等）對映 PatentMind 的 Q17 deadline 模組（`deadline.py`，多管轄假日表）。OA 答辯的「指定期間」長度屬**程序細節，標為「待查證」**（見文末清單）。

## 3. 說明書結構與台灣法定要求（法 §26 + 施行細則 §17）

### 3.1 法定結構（施行細則第 17 條，已查證）

申請發明專利者，說明書應依**下列順序、附加標題**載明（施行細則 §17 第 1 項，第 2 項要求依序撰寫並加標題）：

| # | 章節 | 內容（法定） | 資料模型含義 |
|---|---|---|---|
| 1 | **發明名稱** | 簡明表達發明 | `title` |
| 2 | **技術領域** | 發明所屬之技術領域 | `tech_field`（可推 IPC/CPC，輔助檢索） |
| 3 | **先前技術** | 申請人所知之先前技術，得檢送相關資料 | `prior_art_section`（與 §2.2 檢索結果連動） |
| 4 | **發明內容** | (a)所欲解決之問題 (b)解決問題之技術手段 (c)對照先前技術之**功效** | `{problem, solution, effect}`——進步性論述的骨幹 |
| 5 | **圖式簡單說明** | 有圖式者，依圖號順序以簡明文字說明 | 連動圖式 |
| 6 | **實施方式** | 記載**一個以上**實施方式，必要時以實施例說明；有圖式應參照圖式 | `embodiments[]`——**支持度的來源**，claim 每個特徵都要在這裡找得到 |
| 7 | **符號說明** | 有圖式者，依圖號/符號順序列出主要符號並說明 | 連動 `element_table.py` |

> 工程含義：說明書是**強結構文件**，可建模成 `Spec = {section_type → text_block[]}`。PatentMind 若要做「說明書 ↔ claim 支持度檢查」，可先把 spec 切成這 7 個 section，再把「實施方式」段落與 element table 當作 claim 特徵的「可支持來源池」。

### 3.2 §26 的三大實質要件（已查證，這是 AI 檢查的核心）

專利法第 26 條把「揭露品質」立成法定要件，**每一項都可被機器近似檢查**：

| 條項 | 要件（白話） | 違反的 OA 類型 | 可機器檢查嗎 |
|---|---|---|---|
| **§26 第 1 項** | 說明書應**明確且充分揭露**，使該領域通常知識者能**理解內容並據以實現**（enablement） | 揭露不充分 / 無法據以實現 | 部分（檢查「claim 特徵是否在 spec 出現」可逼近，但「能否實現」需專業判斷） |
| **§26 第 2 項** | 請求項應界定範圍；得一項或多項，各項以**明確、簡潔**方式記載，且**必須為說明書所支持**（clarity + conciseness + support） | 不明確（112-type，含**先行詞 antecedent basis**）、未為說明書支持（26-4 support） | **是**——一致性與支持度是 lint 問題 |
| **§26 第 3 項** | **摘要**僅供技術資訊揭露之用，**不得用於解釋專利權範圍、不得作為揭露是否充分之依據** | （限制條款） | n/a |

> ⚠️ **PatentMind 現況對映**：`prompts/parse_oa.yaml` 已內建「§26 第 2 項 + 先行詞/未見 → `antecedent_basis`」的映射規則，且 `prompts/draft_response.yaml` 內建「antecedent_basis → 引用 §26-2（瑕疵）+ §43-2（修正依據）」的答辯樣板。也就是說，**OA 答辯側已經把 §26 的常見瑕疵流程化了**；撰稿側（申請階段）目前還沒有對應的「事前避免 §26 瑕疵」lint，這是明確的擴充機會（見 §6）。

### 3.3 「支持要件」是一張可檢查的圖（最重要的工程觀念）

「請求項必須為說明書所支持」（§26-2）= **claim 中出現的每個技術特徵，都要能在說明書找到對應揭露**。把它建模成圖：

```
claim_feature("一散熱片，其截面為非均勻") ──支持？──> spec_block("散熱片 200 之微流道 300 具非均勻截面 305")
claim_feature("一無線充電模組")          ──支持？──> ❌ 說明書未提及  ⇒ §26-2 支持要件瑕疵風險
```

- **節點**：claim 的技術特徵（從 claim 文字斷出）、spec 的揭露段落、element table 的元件。
- **邊**：「支持」關係（特徵 ↔ 段落）、「依附」關係（claim ↔ claim，`claim_tree.py`）、「同名」關係（術語一致性）。
- **AI 任務**：找出**沒有支持邊**的 claim 特徵（高風險）、**術語不一致**（同物異名 / 異物同名）、**先行詞缺失**（claim 用「該 X」但前文未先以「一 X」引入）。

## 4. 請求項（Claim）撰寫實務

### 4.1 獨立項 vs 附屬項

- **獨立項（independent claim）**：自成範圍，不依附其他項。最廣、最重要、最決定價值。`claim_tree.py` 的 `is_independent=True`、`depth=0`。
- **附屬項（dependent claim）**：依附某項，包含被依附項全部特徵 + 自己額外特徵。**範圍更窄**。形式：「如請求項 1 所述之…，其中…」（`claim_tree.py` 的 `_DEPENDENCY_PATTERNS` 就是在抓這個句型）。

> 直覺校正（給工程師）：**附屬項範圍是「被依附項 ∩ 自己特徵」，永遠比父項窄**。depth 越深範圍越窄。畫成樹時，根（獨立項）最廣，葉最窄。

### 4.2 Claim 佈局策略（上位/下位、多重附屬）

| 策略 | 說明 | 目的 | 資料模型 |
|---|---|---|---|
| **上位 / 下位（generic / specific）** | 獨立項用上位概念（如「緊固件」），附屬項收斂到下位（「螺栓」「鉚釘」） | 上位求廣度，下位求穩固性（被前案打到上位時，退守下位仍有保護） | 特徵的抽象層級 `genus/species` |
| **逐層收斂的附屬項階梯** | 1（最廣）→ 2、3、4…每層加一個限制 | 為審查答辯**預留退路**：被核駁時可往下層併入 | claim tree 的 depth ladder |
| **多重附屬（multiple dependent）** | 「如請求項 1 或 2 所述」一項依附多個父項 | 用較少項數涵蓋多種組合 | `claim_tree.py` 的 `parents[]`（多父）——已支援 |
| **不同範疇獨立項** | 物的獨立項 + 方法的獨立項 + 系統獨立項，圍同一發明 | 多面向保護（侵權態樣不同） | 多棵 tree / 多 root |

> 註：台灣對多重附屬項是否可再依附另一多重附屬項有**規費與形式限制**（與美國 MPEP 規則不同），**標為「待查證」**（文末）。

### 4.3 Claim 用語與支持

- **用語一致**：同一元件全文同名；claim 用語要在 spec 出現（支持要件）。
- **先行詞（antecedent basis）**：第一次提到某元件用「**一** X」（不定，introduce），之後用「**該** X」（定指，refer back）。若直接用「該 X」而前文沒「一 X」→ **先行詞瑕疵**（§26-2 不明確）。這正是 PatentMind OA 模組最常處理的 rejection 類型（見 `parse_oa.yaml` few-shot）。
- **明確 + 簡潔**：避免相對用語無界定（「大約」「高」）、避免功能性過廣請求。

### 4.4 單一性（§33，已查證）

專利法 §33：「申請發明專利，應就每一發明提出申請。二個以上發明，**屬於一個廣義發明概念**者，得於一申請案中提出申請。」

- **白話**：一案原則上一發明；多個發明若共享「相同或對應之**特別技術特徵（special technical feature）**」（即對先前技術有貢獻的技術特徵），才能放同一案。
- **不符單一性**會收到核駁，需**分割申請（§34）**。
- **資料模型含義**：判斷各獨立項間是否共享 special technical feature——需要「特徵集合的交集 + 該特徵是否相對前案有新穎貢獻」的判斷，**部分可機器輔助（特徵集合比對），但「是否為特別技術特徵」需結合前案判斷**。

### 4.5 與美國 claim 寫法的差異（給寫過 US claim 的工程師）

| 維度 | 台灣 TIPO | 美國 USPTO |
|---|---|---|
| 連接詞 | 「包含」≈ open-ended（comprising） | comprising(開放) / consisting of(封閉) 區分嚴格 |
| 依附句型 | 「如請求項 N 所述之…，其中…」 | "The X of claim N, wherein…" |
| **吉普森式（Jepson / two-part form）** | **不強制**。台灣可用「前言＋特徵子句（其特徵在於…）」的兩段式，但實務上**較少用**、非必要 | 美國 Jepson（"…wherein the improvement comprises…"）會被視為**自認前言為先前技術**，有禁反言風險，故美國實務多避用 | 
| 功能手段用語（means-plus-function） | 有對應規範，解釋回說明書對應結構 | §112(f)，解釋限縮到 spec 揭露結構 + 均等 |
| 多重附屬再依附多重附屬 | 限制 + 規費（待查證細節） | MPEP 不允許 multiple-dependent 再依附 multiple-dependent |
| 一案項數/規費結構 | TIPO 規費結構（待查證） | 超過 3 獨立項 / 20 總項加費 |

> **two-part form 的工程重點**：歐洲（EPO）偏好 two-part form（前言放已知特徵、characterising portion 放新特徵）；台灣審查基準容許但不強制；美國因禁反言而避用。如果系統要**跨管轄轉寫 claim**（TW↔US↔EP），two-part ↔ single-part 的轉換是一個明確的功能點，且**轉換會改變法律意涵（哪些算先前技術自認），不能純文字 reformat**——必須由專利師判斷。

## 5. 撰稿階段的真實痛點（這決定 AI 該插在哪）

| 痛點 | 具體樣貌 | 對 AI 的需求 |
|---|---|---|
| **時間壓力 / 工時黑洞** | 一件中等案 spec 撰稿 8–20+ 工時；事務所論件計酬，工時直接吃利潤 | 草稿生成把「白紙到 70%」的時間砍掉 |
| **與發明人來回** | 發明人交底不完整、補件慢、後來才想到新實施例 | 用交底表結構化提問、自動標出「claim 有特徵但交底沒講清楚」的缺口 |
| **用語一致性** | 同元件多名、claim 與 spec 不同名、符號與內文不一致 | 確定性 lint（術語表 + 符號表比對）——**AI 強項、低風險** |
| **支持度（§26-2）** | claim 寫了 spec 沒揭露；事後 OA 才爆 | 「claim 特徵 ↔ spec 段落」支持度檢查，事前提示缺口 |
| **先前技術查得不夠** | 漏關鍵前案，審查/訴訟才出事 | RAG 檢索擴召回、同義詞/跨語言、相似度排序（Q6/Q7） |
| **claim 範圍拿捏** | 廣窄拉扯，沒有標準答案 | AI 可**提示**「此特徵讓範圍變窄/此前案可能打到獨立項」，但**範圍決策是專利師的** |
| **品質 vs 工時** | 趕件時 spec 偷工，支持度與一致性下降 | lint + 草稿讓「快」與「穩」較不衝突 |

## 6. 對 AI 系統的含義（對映 PatentMind 模組）

### 6.1 可被 AI 輔助的步驟（綠燈，但仍須人類審閱）

| 步驟 | AI 能做什麼 | 風險 | PatentMind 現有 / 可擴充模組 |
|---|---|---|---|
| **草稿生成** | spec 各 section 初稿、claim 初稿、摘要、答辯書草稿 | 中（可能編造/過廣） | 答辯側已有 `prompts/draft_response.yaml`（四段式 + grounding）；**撰稿側 spec/claim 生成 prompt 尚未建** ← 擴充點 |
| **claim 一致性檢查** | 依附關係、多父、forward-reference 偵測 | 低（確定性） | ✅ `claim_tree.py`（純 regex，已實作 TW/CN/US 句型） |
| **說明書 ↔ claim 支持度檢查** | 找出「claim 有、spec 無」的特徵 | 低–中 | **尚未建**——可結合 `element_table.py` + spec 分段 + RAG（§3.3 的圖）← 高價值擴充點 |
| **元件/符號表一致性** | reference numeral ↔ 描述抽取、本案↔引證案數字對應 | 低（確定性） | ✅ `element_table.py`（`extract_element_table` + `correlate`） |
| **前案檢索** | 語意/關鍵字檢索、相似度排序、grounded set | 中（召回不全） | ✅ `rag.py`（Q6 chunking / Q7 Qdrant per-tenant / EMBEDDING bge-m3） |
| **用語表（terminology）** | 維護 term ↔ 標準譯名 ↔ 元件，跨 claim/spec 統一 | 低 | per-tenant 字典機制已存在（`masking.py` 的 `data/tenant_dicts/`），可借用同模式做術語表 ← 擴充點 |
| **citation grounding 驗證** | 答辯/spec 只能引用 grounded set | 低（硬牆） | ✅ `prompts/verify_citations.yaml` + Q14 independent verifier |

### 6.2 絕不能讓 AI 全自動的部分（紅燈 — 簽核責任）

對映 PatentMind 設計不變量（CLAUDE.md §4、§9）：

1. **claim 範圍最終決策**：廣窄拿捏決定專利價值與訴訟成敗，**必須專利師定**。AI 只提示風險。
2. **專利性 go/no-go 結論**：新穎性/進步性是法律判斷，AI 只做比對佐證，不下結論。
3. **送件 / 簽核**：送件是法律行為，責任在署名專利師。系統必須 `draft → human review → sign-off`（對映 Q16 signoff / provenance）。**不可自動送件**。
4. **citation 不可編造**：任何引用（前案編號、案名、條號）必須來自 grounded set，由 verifier 硬牆把關（Q14，「Don't skip the verifier」）。撰稿生成同理——AI 寫的 spec/claim 引用的前案，必須能對回檢索結果。
5. **跨管轄 claim 轉寫的法律意涵**（two-part ↔ single-part、§112(f) means+function）：改寫會改變「哪些算先前技術自認」，須人類判斷，非純文字 reformat。

### 6.3 設計原則小結（與 repo 既有哲學一致）

- **能用確定性就不丟 LLM**：`claim_tree.py` / `element_table.py` 用純 regex，正是這個原則。撰稿側的「一致性 lint / 符號表 / 支持度初篩」也應優先走確定性，把 LLM 留給「生成」與「語意支持度判斷」。
- **所有生成都進 grounding + verifier**：撰稿生成的 spec/claim 也應有「特徵是否有揭露來源」「引用是否在 grounded set」的驗證，比照答辯側的 Q14 硬牆。
- **流程強制人類簽核點**：撰稿 → 審閱 → 簽核 → 送件，每個責任轉移點留 provenance（Q16）。

## 9. 「待查證」清單（送 production 前務必由台灣執業專利師/最新基準確認）

1. **OA 答辯「指定期間」的確切長度**（§46 通知限期申復的天數，以及可否延展、延展次數）——本文僅確認「通知限期申復」之機制，未確認天數。屬 Q17 deadline 模組需要的精確程序值。
2. **多重附屬項的形式限制**：台灣是否允許「多重附屬項再依附另一多重附屬項」、相關規費級距。本文僅標明與美國 MPEP 不同，細節待查。
3. **§22 進步性判斷基準的最新版本**（審查基準第二篇相關章節的現行修正版次與「輔助判斷因素」清單）——進步性是 AI 最不該下結論的部分，但若要做「輔助比對」需對齊最新基準用語。
4. **claim 項數 / 獨立項數的規費結構**（TIPO 是否如 USPTO 對超量項數加費）——影響 claim 佈局策略建議。
5. **設計專利「衍生設計」「成組設計」「部分設計」「圖像設計」的撰稿細節**——本文聚焦發明，設計只給概觀；若系統要支援設計案需另開專文查證。
6. **§34 分割申請的時點限制**（可分割的階段與期限）——與單一性核駁的應對流程相關。
7. **新型專利技術報告代碼（1–6）的完整定義**——本文僅以「代碼 6 = 查無足以否定之前案」為例，完整對照表待查。

> 凡標「待查證」者，PatentMind 不應將其硬編為法律事實對外輸出；若 AI 生成內容觸及這些程序值，應走 Q14 verifier 並標註「需專利師確認」。
